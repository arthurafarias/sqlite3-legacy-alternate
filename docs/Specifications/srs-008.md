# SRS-008: Warning-Clean Compilation (`-Wall -pedantic -Werror`)

`CMakeLists.txt` currently sets no warning flags at all — `sqlite3-legacy-alternate`
and `sqlite3-legacy-alternate-verify` both compile with whatever the default
diagnostic level of the invoking compiler happens to be, and nothing fails
the build no matter what a compiler flags. srs-008 turns `-Wall -pedantic`
into a hard gate: `target_compile_options` adds `-Wall -pedantic -Werror` to
both targets, and every file under `src/sqlite/` is made to build clean
against it first, so flipping the flag on doesn't immediately break the
build it's meant to protect.

Unlike [srs-002](srs-002.md)/[srs-003](srs-003.md), this needs no
`srs-008.md.d/` worked example — like [srs-004](srs-004.md)/[srs-005](srs-005.md)/
[srs-006](srs-006.md), it operates directly on the real tree, and the fix
for each warning is small enough to record inline in the rules below rather
than prototype separately. It's also independent of [srs-007](srs-007.md)'s
method-table collapse: that rewrites call sites, this only touches
diagnostics at the sites it doesn't move — order between the two doesn't
matter, though re-running the probe below after srs-007 lands is cheap
insurance against it introducing a new warning class.

## Baseline

Measured against the current tree (`cmake -S . -B build
-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`, then every entry in
`build/compile_commands.json` re-run with `-fsyntax-only -Wall -pedantic`
appended, `-o`/`-c` stripped, deduplicated by `file:line:col` since a shared
header is parsed once per including TU):

| Compiler | Unique warning sites | Files touched | Categories |
|---|---:|---:|---|
| clang (the compiler `build/`'s cache currently pins) | 173 | 28 | 7 |
| gcc (what a cache-less `cmake -S . -B build` gets, since nothing pins a compiler in `CMakeLists.txt`) | ~39 | ~22 | 2 |

Zero `error:` diagnostics either way — this is entirely a warning cleanup,
not a correctness rescue.

```
119  -Wparentheses-equality   (clang only)
 24  -Wpedantic
 16  -Wchar-subscripts
  4  -Wgnu-empty-struct       (clang only; gcc reports the same 4 sites as -Wpedantic)
  3  -Wempty-translation-unit (clang only; gcc reports the same 3 sites as -Wpedantic)
  1  -Wself-assign            (clang only)
  1  -Wvisibility             (clang only)
```

gcc's diagnostics are a strict subset of clang's here — every gcc-flagged
site is also flagged by clang (as `-Wpedantic`, `-Wchar-subscripts`, or one
of clang's finer-grained names for the same root cause). Rule 3 below makes
that the basis for a one-pass fix.

## Rules

1. **The flags land on both compiled targets, unconditionally, once the
   tree is clean.** `target_compile_options(${PROJECT_NAME} PRIVATE -Wall
   -pedantic -Werror)` and the same on `${PROJECT_NAME}-verify`, added
   straight to `CMakeLists.txt` with no toggle/option guarding it off —
   matching this project's existing minimal-config style (no flags today,
   not "flags behind a cache variable"). There's nothing to opt out of once
   applied: a clean tree stays clean under `-Werror` as long as new code
   respects the same rules, and CI/local builds shouldn't be able to
   silently skip the gate.

2. **The dialect stays `gnu23`, not `c23`.** `target_compile_features(...
   c_std_23)` already resolves to `-std=gnu23` (confirmed in
   `compile_commands.json`), and code under `src/sqlite/` genuinely needs
   GNU extensions — `ReusableSpace.c` sets `_GNU_SOURCE` directly, and the
   `unix*` backend files rely on POSIX/GNU surface `-std=c23` (strict ISO)
   would hide behind feature-test guards. `-pedantic` still does its job
   alongside `gnu23`: it warns on non-ISO *constructs* (the empty structs,
   the empty translation units below) without disabling the GNU
   *extensions* the backend needs. Switching to `-std=c23` is out of scope.

3. **The gate is gcc ∪ clang — verify both, don't assume one subsumes the
   other.** Nothing in `CMakeLists.txt` pins a compiler — `build/`'s cache
   happens to point at `/usr/bin/clang` today, but a fresh checkout with no
   `CC` set picks up system `cc` (gcc, on this box). Both must build
   warning-clean, since "full enforcement" that only holds under one
   contributor's toolchain isn't full enforcement. The baseline table above
   made it *look* like a one-pass problem — every gcc finding matched a
   clang category — but that turned out to be true only for the pre-existing
   baseline, not in general: applying rules 4-9 to clear clang's list and
   then re-probing under gcc surfaced three more sites gcc catches that
   clang never flagged at any point (rule 11). The corrected version of this
   rule: fix to clang's list first since it's the larger starting set, but
   always re-probe under gcc afterward rather than assuming the subset
   relationship holds once the tree changes.

4. **`-Wparentheses-equality` (119 sites, e.g.
   [`BtCursor.c:593`](../../src/sqlite/BtCursor.c)) — drop the redundant
   outer parens.** `if ((pCur->eState == 0))` becomes
   `if (pCur->eState == 0)`. This is leftover style from the amalgamation
   decomposition, not a guarded assignment-vs-comparison idiom (those read
   `if ((rc = foo()) != 0)` — assignment inside real parens, not a bare
   comparison double-wrapped) — mechanical, no semantic risk, `clang-format`
   after.

5. **`-Wchar-subscripts` (16 sites, e.g.
   [`BtCursor.c:461`](../../src/sqlite/BtCursor.c)) — cast the index to
   `int` at the subscript.** `pCur->aiIdx[pCur->iPage]` becomes
   `pCur->aiIdx[(int)pCur->iPage]`. `iPage` and similar fields are `i8`
   (signed char) by original SQLite design to keep `BtCursor` small; the
   warning exists because a *negative* `char` subscript is a real bug
   pattern elsewhere in C, but here the field's range is already bounds-
   checked (`BtCursor.c:455`'s `iPage >= (20 - 1)` guard) — an explicit cast
   documents "checked, not a bug" rather than silencing the class of bug the
   warning exists to catch.

6. **`-Wpedantic` function-pointer/`void *` sites (24 sites, all in
   [`sqlite3.c`](../../src/sqlite/sqlite3.c)'s math-function registration
   table) — apply the cast idiom already used 114 times elsewhere in the
   same file.** ISO C doesn't guarantee a function pointer fits in
   `void *`; `sqlite3.c` already has the answer for this, used for every
   `0`-valued table entry: `(void *)(intptr_t)fn`. The ~21 named-function
   entries that predate that convention (`(void *)&globInfo`, bare `xCeil`,
   `likeFunc`, `ceilingFunc`, `trunc` in the `FuncDef` table around
   `sqlite3.c:7270-7280`) get the same wrap. Extending an existing,
   already-reviewed idiom to the stragglers, not inventing a new one.

7. **`-Wgnu-empty-struct` / the matching `-Wpedantic` "struct has no
   members" under gcc (4 sites: [`Fts5Context.h`](../../src/sqlite/Fts5Context.h),
   [`Fts5Tokenizer.h`](../../src/sqlite/Fts5Tokenizer.h),
   [`KeyClass.h`](../../src/sqlite/KeyClass.h),
   [`sqlite3_blob.h`](../../src/sqlite/sqlite3_blob.h)) — drop the `{}`
   body, keep the bare forward declaration.** All four are opaque handle
   types (`sqlite3_blob` is real public API; the other three are internal
   opaques) that upstream SQLite never defines by this name in a header at
   all — real `sqlite3_blob` is `typedef struct sqlite3_blob sqlite3_blob;`
   with no body anywhere the public API can see. The container-extraction
   pass that split the amalgamation ([`architecture.md`](../architecture.md#the-container-convention))
   over-materialized these into empty definitions where the original had
   only a forward declaration. `struct sqlite3_blob {};` becomes
   `struct sqlite3_blob;` (kept alongside the existing `typedef`) — this is
   strictly more correct, not just quieter: it stops any `.c` file from
   being able to `sizeof`/dereference a handle that's supposed to be
   opaque.

8. **`-Wself-assign` / the matching dead code (1 site,
   [`ReusableSpace.c:7`](../../src/sqlite/ReusableSpace.c)) — delete the
   statement.** `nByte = (nByte);` is a no-op; nothing downstream depends on
   the assignment happening. Remove the line entirely.

9. **`-Wvisibility` (1 site,
   [`unixFile.h:46`](../../src/sqlite/unixFile.h)) — declare `struct flock`
   before it's used as a parameter type.** `unixFileLock(unixFile *,
   struct flock *)` implicitly declares a new, function-scope-only `struct
   flock` tag because nothing in the header pulls in the real one from
   `<fcntl.h>`. Add `struct flock;` as a file-scope forward declaration (the
   real struct is defined by the system header the corresponding `.c`
   already includes) so the parameter refers to the same type callers see.

10. **`-Wempty-translation-unit` (3 sites — [`sqlite3_hard_heap.c`](../../src/sqlite/sqlite3_hard_heap.c),
    [`sqlite3_libversion.c`](../../src/sqlite/sqlite3_libversion.c),
    [`sqlite3_soft_heap.c`](../../src/sqlite/sqlite3_soft_heap.c)) — held
    back for a human decision, not auto-fixed.** These three files are
    completely empty: zero bytes, no declaration, ISO C forbids compiling
    them as a standalone translation unit at all. Two ways to resolve each,
    and picking between them requires knowing what the container-extraction
    pass intended, not something this document can infer:
    - the container is genuinely dead (whatever symbol it was meant to hold
      was placed elsewhere, or never existed) — delete the `.c`/`.h` pair
      and drop the include, if any;
    - the container is a real gap — the corresponding header declares
      something with no definition anywhere else in the tree — and the
      body needs to be restored from the amalgamation source.
    `git log -- src/sqlite/sqlite3_libversion.*` (and the other two) is the
    starting point for telling those two cases apart before srs-008 can be
    applied tree-wide.

## Tooling

No new `tools/clang-refactor/` script — unlike srs-004/005/006, this isn't
one mechanical AST rewrite repeated hundreds of times, it's seven small,
heterogeneous fix patterns across 28 files (173 sites, more than half of
them one single pattern covered by rule 4). The existing compile database
is enough to find and verify every site directly:

```sh
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
python3 - <<'EOF'
import json, subprocess, shlex
for e in json.load(open("build/compile_commands.json")):
    args = [a for a in shlex.split(e["command"]) if a not in ("-c",)]
    # ...append -Wall -pedantic -fsyntax-only, drop -o <file>, run, inspect stderr
EOF
```

is the same probe used to produce the Baseline table above — re-run it
after each rule's fix lands to confirm that category's count drops to zero
before moving to the next. Once every rule (including the rule 10 decision)
is applied and the probe reports zero warnings under both `clang` and `cc`
(gcc), rule 1's `target_compile_options` change lands as the last commit —
at that point the compiler itself is the enforcement mechanism and there's
nothing further to run by hand.

## Status

Not yet applied. `CMakeLists.txt` carries no warning flags yet; all 173
(clang) / ~39 (gcc) baseline sites above are still present. Rule 10's three
empty translation units are a blocking decision — dead-vs-restore needs to
be resolved for each before the tree can build clean, since deleting one
that turns out to matter and restoring one that turns out to be genuinely
dead both need to happen before `-Werror` can be turned on unconditionally.

## Applying

1. Resolve rule 10's three held-back files by hand (delete or restore).
2. Apply rules 4-9 in any order — they touch disjoint sites, no rule's fix
   depends on another's having landed first.
3. Re-run the probe above under both `clang` and `cc` (gcc); confirm zero
   warnings from each.
4. Add `-Wall -pedantic -Werror` to both targets' `target_compile_options`
   in `CMakeLists.txt` (rule 1).
5. Rebuild and verify against the real library, the same check every prior
   SRS in this directory ends on:

   ```sh
   cmake -S . -B build
   cmake --build build
   ctest --test-dir build --output-on-failure
   ```

   A passing `sqlite3-legacy-alternate-verify` run after step 4 confirms
   the warning cleanup didn't change observable behavior — same property
   srs-003 through srs-006 each check on landing.
