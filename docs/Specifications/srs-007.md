# SRS-007: Method-Table Indirection Removal

`src/sqlite/` still calls every pluggable subsystem the way the upstream
amalgamation does: through a `struct` of function pointers stored on an
instance and invoked as `pThing->xMethod(pThing, ...)`. srs-006 already names
this pattern explicitly — module 1 in its table describes
`sqlite3-backend-os` as "OS abstraction dispatch — the indirection through a
VFS's function-pointer tables, not the concrete syscalls behind them." srs-007
generalizes that observation to the five other method-table families in the
tree and specifies how to collapse each internal call site to a direct call
against this build's actual implementation, without deleting the public
registration API those tables exist to serve.

## Relationship to prior SRS

- **srs-004** rule 4 and **srs-006** rule 1 both exempt the real public API
  (`sqlite3_vfs`, `sqlite3_module`, `sqlite3_pcache_methods2`, ...) from their
  renaming passes specifically because external callers link against those
  symbols by name. srs-007 keeps that exemption: the six struct *types* and
  the registration entry points that let a caller populate one at runtime
  (`sqlite3_vfs_register`, `sqlite3_create_module`,
  `sqlite3_config(SQLITE_CONFIG_MALLOC/PCACHE2/MUTEX, ...)`) are unchanged.
  What changes is which code path this tree's own internal callers take to
  reach the *built-in* implementation — today that's unconditionally through
  the pointer table; after srs-007 it's a direct call, with the table
  relegated to a fallback reached only when a caller has actually overridden
  the default.
- Independent of srs-002/srs-003's per-library C++ pipeline (this document
  only concerns `sqlite3-legacy-alternate`'s own decomposition), but it
  should land **before** srs-004's naming pass is run tree-wide: collapsing a
  dispatch site rewrites its call expression, and doing that once against
  `sqlite3OsRead`/`id->pMethods->xRead(...)`-style names is cheaper than
  doing it once now and again after every call site is renamed to
  `sqlite3_os_read`/snake_case form.

## Inventory

Six struct-of-function-pointer types were found under `src/sqlite/*.h`
(`grep -c '(\s*\*\s*x[A-Z]' *.h`), ranked by how many concrete
implementations actually exist in this tree today versus how many internal
call sites indirect through them:

| Type | Fields | Built-in impl. count | Internal call sites | Selection mechanism |
|---|---|---|---|---|
| `sqlite3_module` | 24 | 1 (a stub — no real vtab is registered; FTS5/RTree exist only as extension-API header stubs, not wired-up modules) | `VTable.c`, `Vdbe.c` (~14 sites) | `sqlite3_create_module` at runtime |
| `sqlite3_vfs` | 16 | 2 (`aVfs[]` in `sqlite3.c`: `"unix"` and `"unix-excl"` — 14 of 16 function pointers are byte-identical between the two; only `pAppData` and the name differ) | `sqlite3_vfs.c` (31 sites, all via `sqlite3Os*` shims) | `sqlite3_vfs_register`, `zVfs` name lookup |
| `sqlite3_io_methods` | 18 | 5 (`posixIoMethods`, `nolockIoMethods`, `dotlockIoMethods` in `sqlite3_io_methods.c`; `memdb_io_methods`; `MemJournalMethods`) | `sqlite3_file.c` (22 sites, all via `sqlite3Os*` shims) | locking mode / file kind, resolved once at `xOpen` |
| `sqlite3_mutex_methods` | 9 | 2 (`sMutex` no-op build in `sqlite3.c:1754`, `sMutex` pthread build in `sqlite3.c:1775`) | `sqlite3.c` (~8 sites via `sqlite3Config.mutex`) | `SQLITE_THREADSAFE` compile-time config |
| `sqlite3_pcache_methods2` | 11 | 1 (`defaultMethods` in `PCache.c:334`) | `PCache.c` (11 sites via `sqlite3Config.pcache2`) | none — always the default in this tree |
| `sqlite3_mem_methods` | 7 | 1 (`defaultMethods` in `Mem.c:93`) | `Mem.c`, `Sqlite3Config.c` | none — always the default in this tree |

The two columns that matter for scoping are implementation count and
selection mechanism, not raw field count — they determine which of the three
rules below a family falls under.

## Rules

1. **Zero-selection families collapse to a true direct call.**
   `sqlite3_pcache_methods2` and `sqlite3_mem_methods` have exactly one
   built-in implementation and nothing in this tree ever chooses a different
   one at runtime. Every internal call site
   (`sqlite3Config.pcache2.xFetch(...)`, `sqlite3Config.mem.xMalloc(...)`,
   etc.) is rewritten to call the concrete function directly
   (`sqlite3PcacheDefaultFetch(...)`), eliminating the struct dereference and
   the indirect branch entirely. The struct instance itself
   (`defaultMethods`) and the `sqlite3_config(SQLITE_CONFIG_PCACHE2/MALLOC,
   ...)` entry point are kept, but only as the landing spot for a caller who
   actually installs a replacement — see rule 4.

2. **Small closed sets resolved by build/open-time configuration collapse to
   a tag + `switch`, not a pointer.** `sqlite3_mutex_methods` (2 impls,
   picked once by `SQLITE_THREADSAFE`) and `sqlite3_vfs` (2 impls that share
   14 of 16 function pointers already) fall here: replace the stored
   function-pointer struct with a small enum discriminant set once at
   init/open time, and turn each of the `sqlite3Os*`/mutex call sites into a
   `switch` over that tag whose case bodies call the concrete functions by
   name. This still isn't a single static call — the underlying choice is
   real, not obfuscation — but the compiler sees fixed, non-overridable call
   targets at every case instead of chasing a pointer loaded from memory, so
   it can inline and devirtualize where the old vtable form couldn't.
   `sqlite3_io_methods` is the same shape in principle (5 impls, one per
   open file, selected at `xOpen`) but is **out of scope for the first
   pass**: `MemFile`/`MemJournal` are genuinely different concrete types
   sharing the `sqlite3_file *` slot with real unix file handles throughout
   the pager/WAL call chain, so collapsing this one touches far more of the
   tree than a call-site rewrite — track it as a follow-on once rules 1–3 are
   applied and there's a real switch-based precedent (rule 2's `sqlite3_vfs`
   pass) to extend.

3. **`sqlite3_module` is deferred, not collapsed.** With exactly one stub
   instance and no real second virtual-table implementation anywhere in this
   tree to compare against, there's no genuine indirection to remove yet —
   only one thing to point at, and no evidence for what the *other* case
   looks like. Collapsing it now would just be rule 1's treatment applied to
   a stub, which produces a direct call that's never validated against real
   virtual-table behavior. Revisit once FTS5 or R-Tree gets a real module
   registration in this tree (their header stubs already exist per the
   inventory table), not before.

4. **The public override path becomes a guarded fallback, not the default
   path.** For every family under rules 1–2, the caller-visible registration
   API (`sqlite3_config(...)`, `sqlite3_vfs_register`) still writes into the
   same struct it does today. What changes is that internal code no longer
   reads through that struct unconditionally: a single flag (set the first
   time a caller successfully overrides the default, checked once per
   subsystem rather than once per call) routes execution back to the
   original indirect-call form only when a non-default implementation is
   actually installed. A build that never calls
   `sqlite3_config(SQLITE_CONFIG_MALLOC, ...)` — the common case, and the
   only case `verify/main.c` exercises — never pays for or executes the
   indirection at all.

## Tooling

No existing `tools/clang-refactor/` script does this rewrite; it needs a new
one, following the same two-phase report/apply shape as
`clang-refactor-scope-extern-consts.py`:

1. **Report.** For each family in the inventory table, find every call
   expression matching `<expr>-><indirection-field>.x<Name>(...)` or
   `<expr>-><indirection-field>-><Name>(...)` via libclang, resolve
   `<indirection-field>` back to the struct member declared in that family's
   header, and classify by rule (1/2/3) per the table above.
2. **Apply.** Rule-1 sites get rewritten in place to the concrete function
   name. Rule-2 sites additionally need the discriminant field added to the
   owning struct (`sqlite3_vfs`'s `pAppData`-equivalent, a `mutex_kind`
   field alongside `sqlite3Config.mutex`) and the call site turned into a
   `switch`. Both need the guard-flag plumbing from rule 4 added once per
   family, not once per call site.

## Verification

Same baseline as srs-003/srs-004 — `sqlite3-legacy-alternate-verify` must
still pass after each family's pass, since it's the only thing in this tree
that exercises the public API surface end to end:

```sh
cmake --build build
ctest --test-dir build --output-on-failure
```

That alone doesn't prove the indirection is actually gone, only that
behavior didn't regress. Confirming the *point* of this SRS — fewer indirect
calls — needs a second check per rule-1/2 family: after the pass, `objdump
-d` (or `-S` against a debug build) on the touched translation unit should
show no `call *%rax`-style indirect call at the collapsed sites, only direct
`call <symbol>` instructions, for the default (no-override) path.

## Status

Draft — not yet applied. This document fixes the inventory, the per-family
rule, and the fallback design before any call site is touched, the same way
srs-002 fixed the iterator shape and srs-004 fixed the naming procedure
