# SRS-004: Identifier Naming Convention

Every type name and function name under `src/sqlite/` is `snake_case`; every
enumeration constant is `SCREAMING_SNAKE_CASE`. Unlike srs-002 and srs-003,
this convention doesn't need new scaffolding to demonstrate it: the
enforcement tool already exists —
[`tools/clang-refactor/clang-refactor-enforce-naming.py`](../../tools/clang-refactor/clang-refactor-enforce-naming.py),
referenced in [`architecture.md`](../architecture.md) — and operates
directly on the real tree rather than a toy example. srs-004 formalizes the
convention that tool enforces and records how to run it and verify its
output, rather than adding a `srs-004.md.d/` worked example.

## Rules

1. **Type names are `snake_case`.** This covers struct/union/enum tags,
   `typedef` names, C++ type aliases, and (if any appear as the tree moves
   toward C++) class names. `Btree` becomes `btree`, `MemPage` becomes
   `mem_page`, `WhereClause` becomes `where_clause`.
2. **Function names are `snake_case`.** `sqlite3BtreeOpen` becomes
   `sqlite3_btree_open`, `walIndexHash` becomes `wal_index_hash`. This is
   the "methods" half of the convention — under the srs-003 container
   convention a function already lives in the header of the type it
   operates on, so renaming it to snake_case doesn't change *where* it
   lives, only what it's called.
3. **Enumeration constants are `SCREAMING_SNAKE_CASE`.** This one is mostly
   already true tree-wide (`SQLITE_OK`, `WO_IN`, ...); the check exists to
   catch the exceptions and hold the line as new code lands.
4. **The genuine public API is out of scope, automatically.** srs-003 rule 3
   had to explicitly test for the `sqlite3_`-prefixed, underscore-separated
   naming pattern to carve public API out of its *visibility* rules. This
   convention doesn't need an equivalent carve-out: `readability-identifier-
   naming`'s `lower_case` style only flags identifiers that don't already
   conform, and the real public surface (`sqlite3_open`, `sqlite3_stmt`,
   `sqlite3_bind_int64`, `sqlite3_context`, ...) is already `snake_case`. It
   passes the check unchanged, not because it's excluded by name, but
   because it already satisfies rule 1/2 on its own. What *does* get
   rewritten is the large internal surface that merely *looks* related to
   that prefix but isn't part of it — `sqlite3BtreeOpen`,
   `sqlite3PagerGet`, and similar internal `sqlite3<Camel>` helpers are
   camelCase today and become `sqlite3_<snake>` under this pass. That's an
   expected, harmless naming *resemblance* to the public API, not a
   collision: they're distinct identifiers, and the tool's collision
   detection (below) would catch it if two of them ever did land on the
   same name.
5. **This is a lint, not a one-shot migration.** Like
   `clang-refactor-scope-extern-consts.py` and the other tree-shaping
   passes, it's meant to be re-run as new code lands under `src/sqlite/`,
   not applied once and forgotten.

## Tooling

`clang-refactor-enforce-naming.py` wraps clang-tidy's
`readability-identifier-naming` check (configured per the casing rules
above) instead of hand-rolling a libclang rename, because for a given
translation unit clang-tidy already finds every declaration *and* every
reference to it in one pass. It follows the same two-phase shape as the
other scripts in `tools/clang-refactor/`:

1. **Report (default, read-only).** Every target `.c` file is sharded
   across worker threads and parsed with `--export-fixes`; nothing is
   written. Proposed renames are merged into one report, grouped by
   `(kind, old_name) -> new_name`. If two distinct symbols of the same kind
   would land on the same new name, every edit for *both* is held back
   under "collisions" for manual review instead of being silently applied.
2. **Apply (`--apply`).** The surviving, collision-free edits are
   deduplicated per file — the same header edited by many translation
   units proposes byte-identical replacements — and spliced in
   offset-descending order, the same technique
   `clang-refactor-struct-to-header.py` and
   `clang-refactor-scope-extern-consts.py` use. `clang-format` runs over
   every touched file afterward.

Sharding read-only across threads and doing the write as a single-threaded
final step matters here specifically: a shared header `#include`d from
`.c` files in different shards would otherwise get `--fix`-ed by multiple
concurrent clang-tidy processes racing to rewrite the same file.

## Running it

Requires a compile database (`CMAKE_EXPORT_COMPILE_COMMANDS=ON`, already the
default for this project's `build/` directory) and `clang-tidy` /
`clang-format` on `PATH`.

```sh
cmake -S . -B build
python3 tools/clang-refactor/clang-refactor-enforce-naming.py \
    --report /tmp/naming-report.json
```

This reports every non-conforming identifier under `src/sqlite/` without
writing anything. Review the collision list (if any) before applying:

```sh
python3 tools/clang-refactor/clang-refactor-enforce-naming.py --apply
```

## Verifying

There's no separate toy example to build here — the check runs on the real
tree, so the real tree's own verification proves it. After `--apply`,
rebuild and run the same verification srs-003 relies on:

```sh
cmake --build build
ctest --test-dir build --output-on-failure
```

`sqlite3-legacy-alternate-verify` links the library through the public
`sqlite3.h` API and drives `sqlite3_open` / `sqlite3_exec` / `sqlite3_close`
against an in-memory database. A passing run after the renaming pass
confirms two things at once: the internal rename didn't break the build
(every internal call site was updated consistently), and the public API
that rule 4 leaves untouched still behaves identically from the outside —
`verify/main.c` never references an internal `sqlite3<Camel>` symbol, only
the public `sqlite3_*` one, so it can't observe the internal rename at all
except through "does the library still work."

## Status

Not yet applied. The tree today is still the pre-rename state described in
[`architecture.md`](../architecture.md) — internal types in
`UpperCamelCase` (`Btree`, `MemPage`, `WhereClause`, ...) and internal
functions in `sqlite3UpperCamel`/`lowerCamelCase` form
(`sqlite3BtreeOpen`, `walIndexHash`, ...). The tool is runnable as-is
(`build/compile_commands.json` exists; `clang-tidy`/`clang-format` are
on `PATH`) — this document exists to fix the convention and the procedure
before that first tree-wide pass is run, the same way srs-002 fixed the
iterator shape before any real container was converted to it.
