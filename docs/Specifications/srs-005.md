# SRS-005: `sqlite3_` Type Prefix Convention

Every struct, union, enum, typedef, and type alias declared under
`src/sqlite/` carries the `sqlite3_` prefix. Roughly a tenth of the tree
already does — the genuine public API types this project must stay
compatible with (`sqlite3_context`, `sqlite3_vfs`, `sqlite3_stmt`'s
neighbors, and the rest of the real SQLite C API) were always spelled this
way. srs-005 extends that same spelling to the internal nine-tenths
(`Btree`, `MemPage`, `Expr`, `i16`, ...) that predate it, so the whole tree
reads as one namespaced library instead of a public API wrapped around an
unprefixed internal one.

This is orthogonal to the two conventions already in place:

- [`srs-003`](srs-003.md) governs where a symbol *lives* — public header vs.
  `static`, `extern` vs. file-local `const`. srs-005 doesn't move anything;
  it only changes how a type's own name is spelled.
- `clang-refactor-enforce-naming.py` (see [`architecture.md`](../architecture.md#the-refactor-toolchain))
  already enforces `lower_case` for the same declaration kinds (struct,
  union, enum, typedef, type alias) as a standing lint. srs-005 folds that
  case normalization into the same pass rather than running two full-tree
  AST rewrites over the same identifiers — see Rule 1.

## Rules

1. **Every type/structure declared under `src/sqlite/` gets the `sqlite3_`
   prefix, normalized to `lower_case`, in one pass.** This covers struct,
   union, and enum tags, `typedef` names, and type aliases —
   `Btree` → `sqlite3_btree`, `BtShared` → `sqlite3_bt_shared`, `MemPage` →
   `sqlite3_mem_page`. There is no kind exception for primitive-width
   aliases: `i16`, `u8`, `u32`, `Pgno`, and the rest of the tree's integer
   typedefs get the prefix exactly like container types do — "every type"
   means every type, not just the ones that look like structs.

2. **A name that already conforms is left alone.** The check is idempotent:
   `sqlite3_context`, `sqlite3_vfs`, and every other already-prefixed,
   already-`lower_case` public API type is skipped, not double-prefixed.
   This is the property that makes the rule safe to apply at all — it
   touches only the internal types this project owns, never the real
   SQLite C API surface the [README](../../README.md) commits to staying
   compatible with.

3. **Functions, enum constants, and variables are out of scope.** srs-005
   governs how a type's *own* name is spelled, not how it's referenced from
   a function signature or macro. Function naming stays with
   `clang-refactor-enforce-naming.py`'s existing `lower_case`/
   `SCREAMING_SNAKE_CASE` rules, unchanged by this SRS.

4. **A case-insensitive collision is held back for manual review, never
   silently merged.** Two distinct symbols that differ only by case
   collapse to the same `lower_case` + `sqlite3_` target name, and C
   doesn't allow two types with one name. The tooling (below) detects this
   automatically and refuses to touch either symbol until it's resolved by
   hand. The tree's one real instance as of this writing:
   [`Fts5Tokenizer`](../../src/sqlite/Fts5Tokenizer.h) (the opaque
   per-tokenizer instance handle, mirroring `sqlite3_vtab_cursor`) and
   [`fts5_tokenizer`](../../src/sqlite/fts5_tokenizer.h) (the
   `xCreate`/`xDelete`/`xTokenize` method-table struct, mirroring
   `sqlite3_module`) are both real upstream FTS5 API names that differ only
   by case, and both would land on `sqlite3_fts5_tokenizer`. The resolution
   pattern for this and any future collision: keep the bare prefixed name
   for whichever side is the *instance* type, and append a role-clarifying
   suffix to the *method-table* side before re-running the tool — here,
   `fts5_tokenizer` → `sqlite3_fts5_tokenizer_module`, leaving
   `Fts5Tokenizer` → `sqlite3_fts5_tokenizer` untouched by the automatic
   pass on the next run.

5. **A rename that lands on a name already in use elsewhere in the tree is
   held back too, even when nothing else is being renamed to that same
   target.** Rule 4's collision check only compares proposed renames
   against *each other*; it can't see a target name that's already correct
   and therefore was never proposed in the first place (Rule 2). Two real
   cases as of this writing, both genuine SQLite identifiers that predate
   this project's decomposition and must not be redefined:
   [`Module`](../../src/sqlite/Module.h) (the per-connection registered
   virtual-table bookkeeping struct — `pModule`/`zName`/`pAux`/`xDestroy`)
   would prefix to `sqlite3_module`, which is already the real, distinct
   public API vtable-methods struct declared in
   [`sqlite3_module.h`](../../src/sqlite/sqlite3_module.h); and
   [`BusyHandler`](../../src/sqlite/BusyHandler.h) (the connection's
   busy-handler callback bookkeeping struct) would prefix to
   `sqlite3_busy_handler`, already the real public API function declared in
   `sqlite3.h`. Same disposition as Rule 4 — held back, resolved by hand:
   `Module` → `sqlite3_module_entry` (this is in fact the same name real
   upstream SQLite uses internally for this exact struct), `BusyHandler` →
   `sqlite3_busy_handler_info`, matching the `_info`-suffix pattern already
   used elsewhere in the tree (`sqlite3_index_info`, `InitData`-style
   bookkeeping types) for "state behind a public entry point" structs.

## Tooling

[`tools/clang-refactor/clang-refactor-prefix-types.py`](../../tools/clang-refactor/clang-refactor-prefix-types.py)
applies this rule, in the same two-phase shape as every other script in
that directory (see
[`architecture.md`](../architecture.md#the-refactor-toolchain)):

1. **Report.** Every `.c` file under `src/sqlite/` in the compile database
   is parsed with clang-tidy's `readability-identifier-naming` check
   (`--export-fixes`, read-only), configured with `StructPrefix` /
   `UnionPrefix` / `EnumPrefix` / `TypedefPrefix` / `TypeAliasPrefix` all
   set to `sqlite3_` alongside the matching `*Case: lower_case`. This is
   the same AST-accurate, cross-TU pass `clang-refactor-enforce-naming.py`
   already relies on for exactly this reason: one parse finds every
   declaration *and* every reference consistently, and re-running it later
   against new code catches drift for free. Proposed renames are merged
   across shards; same-target collisions (Rule 4) are held back and
   reported instead of applied. A second pass then scans every `.c`/`.h`
   file under `src/sqlite/` for the proposed target names as plain text
   and holds back anything that's already in use elsewhere in the tree
   (Rule 5) — the check `build_report()`'s in-batch grouping can't do on
   its own, since an already-conforming name never shows up in clang-tidy's
   diagnostics to begin with.
2. **Apply.** With `--apply`, the surviving edits are deduplicated per file
   and spliced in offset-descending order — no dependency on the separate
   `clang-apply-replacements` binary, matching
   `clang-refactor-struct-to-header.py` and
   `clang-refactor-enforce-naming.py`. `clang-format` runs over every
   touched file afterward.
3. **Verify.** With `--apply` (on by default, `--no-verify` to skip),
   `clangd --check` re-typechecks every touched file against the same
   compile database, rebuilding clangd's own index for each file post-edit.
   This is a second, independently-implemented pass over the same edits —
   clang-tidy's fix-its are already AST-derived and correct by
   construction for the translation units it parses, so `--verify` isn't a
   second rename; it's a check that nothing referencing a renamed symbol
   from outside those TUs (or from a spot clang-tidy's sharding missed)
   was left unresolved.

Run with no `--apply` first: it only reports. Nothing is written until you
pass `--apply`, same convention as every other script in
`tools/clang-refactor/`.

## Current state

As of this writing, running the report phase against the full tree:

```sh
python3 tools/clang-refactor/clang-refactor-prefix-types.py --report /tmp/prefix-report.json
```

finds 467 clean renames across 281 `.c` files' worth of declarations:

| Kind    | Count |
|---------|------:|
| struct  |   213 |
| typedef |   249 |
| union   |     5 |
| enum    |     0 |

(No bare enum tags are non-conforming — most enums in the tree are
anonymous, carrying only constants, which are out of scope per Rule 3.)

Plus 8 held-back identifiers needing manual resolution before they can be
applied: one Rule 4 collision (`Fts5Tokenizer` / `fts5_tokenizer`, 4
identifiers across the struct/typedef kinds), and two Rule 5 conflicts
(`Module`, `BusyHandler`, likewise 4 identifiers across struct/typedef).

## Applying

Not yet applied tree-wide — like [`srs-002`](srs-002.md), this is a
standing rule with tooling in place, not yet run to completion. The path to
applying it:

1. Resolve the three held-back cases by hand: the `Fts5Tokenizer`/
   `fts5_tokenizer` collision (Rule 4) and the `Module`/`BusyHandler`
   conflicts (Rule 5), so the automatic pass has no remaining ambiguity.
2. `python3 tools/clang-refactor/clang-refactor-prefix-types.py --apply`
3. Rebuild and verify against the real library, the same way
   [`srs-003`](srs-003.md#verifying-the-real-tree) does — since this rule
   renames internal types only, never exported C API function names, the
   existing `sqlite3-legacy-alternate-verify` target is still the right
   compatibility check:

   ```sh
   cmake -S . -B build
   cmake --build build
   ctest --test-dir build --output-on-failure
   ```

   A passing run still prints `srs-003 real-library verification: PASS` —
   srs-005 touching every internal type name and that verification still
   passing unmodified is the actual proof this rule preserves the public
   API surface it's meant to leave alone.
