# SRS-003: Façade Visibility Convention

A standing TODO, in the same spirit as [srs-002](srs-002.md): apply the
rules below to every type in `src/sqlite/`, following the worked example in
[`srs-003.md.d/facade-pattern-example/`](srs-003.md.d/facade-pattern-example/).
Not yet applied to any real container — see
[`architecture.md`](../architecture.md) for the current state of the
one-file-per-symbol tree this builds on.

Where srs-002 governs how an iterable *behaves* (alloc/construct/destruct,
iterator, predicate search), srs-003 governs where a symbol *lives* and
whether it's visible outside its own translation unit. The two compose: a
`list` container built to the srs-002 shape still has its methods placed
according to the rules below.

## Rules

1. **One type per header.** A `.h` under `src/sqlite/` declares exactly one
   struct/typedef. This is already the tree's container convention
   (`Btree.h`, `Select.h`, `i16.h`, ...); srs-003 only adds visibility rules
   on top of it.

2. **A method belongs to the header of the type it operates on**, decided by
   two ordered tests:
   - **First-argument mutation**: if the function's first parameter is
     `T *` and the function mutates that `T` instance (and, if it touches
     other structs at all, does so only as read-only input), it's declared
     in `T.h`. This is the common case: `db_exec(db *self, const char *sql)`
     lives in [`db.h`](srs-003.md.d/facade-pattern-example/db.h).
   - **Return-type fallback**: otherwise, if it returns `T *`, it's declared
     in `T.h`. This covers factories/allocators that have no `self` yet —
     `stmt_create(db *owner, const char *value)` returns `stmt *` and has no
     `stmt` to mutate, so it lives in
     [`stmt.h`](srs-003.md.d/facade-pattern-example/stmt.h) even though its
     first argument is a `db *`.
   - When both tests could apply — a function mutates its first-argument
     type *and* returns a pointer to some other type — first-argument
     mutation wins. `db_prepare(db *self, const char *sql)` mutates `self`
     and returns `stmt *`; it's declared in `db.h`, not `stmt.h`, because the
     mutation test is checked first.
   - **Read-only accessors** (`stmt_column_text`) don't "mutate" anything,
     but they're part of the type's stable public contract in the same way
     a getter is part of a class's public interface, so they're declared in
     the header alongside the mutators. The mutation clause exists to keep
     unrelated utility functions out of `T.h`, not to exclude accessors —
     see rule 3 for how to tell the two apart.

3. **Everything else is private**, and private has two shapes depending on
   how many translation units need it:
   - **Used from one `.c` file**: `static`, declared and defined in that
     file, no header entry at all. `find_row` and `insert_row` in
     [`db.c`](srs-003.md.d/facade-pattern-example/db.c) are internal
     implementation helpers for `db_exec`/`db_prepare` — never part of
     `db`'s public contract — so they stay static in `db.c` even though
     their signatures look like they could be public accessors.
   - **Used from more than one `.c` file, but no type owns it**: a
     standalone header/source pair with no struct in it, named for what it
     does rather than for a type. `fnv1a_hash` is used by both `db.c` and
     `stmt.c`, so it gets its own
     [`hash.h`](srs-003.md.d/facade-pattern-example/hash.h) /
     [`hash.c`](srs-003.md.d/facade-pattern-example/hash.c) pair instead of
     being duplicated or promoted into either type's header.

4. **A `const` singleton used from more than one translation unit** is
   declared `extern` in the header of the type it's an instance of, and
   defined in that type's `.c`. [`db_limits.h`](srs-003.md.d/facade-pattern-example/db_limits.h)
   declares `extern const db_limits db_limits_default;`;
   [`db_limits.c`](srs-003.md.d/facade-pattern-example/db_limits.c) defines
   it. `db.c` and `verify.c` both read it, which is exactly what makes it a
   rule-4 case rather than a rule-5 one.

5. **A `const` object used from exactly one translation unit** stays
   `static const`, declared and defined in that file, never `extern` and
   never in a header. `FNV1A_OFFSET_BASIS` and `FNV1A_PRIME` in
   [`hash.c`](srs-003.md.d/facade-pattern-example/hash.c) are only read
   inside `fnv1a_hash`, so they're private to that file even though
   `hash.c` itself is a multi-TU utility under rule 3.

## Worked example

[`srs-003.md.d/facade-pattern-example/`](srs-003.md.d/facade-pattern-example/)
is a small but real (not stubbed-out) sqlite3-shaped facade: `db` (rules 1,
2, 3) and `stmt` (rules 1, 2) as the two public types, `db_limits` as a
singleton-constant type (rule 4), and `hash` as a standalone multi-TU
utility with its own private constants (rules 3 and 5).

[`verify.c`](srs-003.md.d/facade-pattern-example/verify.c) is the
verification executable: a minimal sqlite3 application —
open / exec / prepare / step / column / finalize / close, in that order —
built against nothing but `db.h`, `stmt.h`, and `db_limits.h`. It links the
facade, exercises every public entry point, and asserts on the results
rather than just returning stub values. Build and run it standalone:

```sh
cmake -S docs/Specifications/srs-003.md.d/facade-pattern-example \
      -B /tmp/facade-example-build
cmake --build /tmp/facade-example-build
ctest --test-dir /tmp/facade-example-build --output-on-failure
```

A passing run prints `srs-003 facade example: PASS` and exits 0. This
CMakeLists.txt is intentionally standalone rather than wired into the root
`CMakeLists.txt` — like `srs-002.md.d`, this directory is documentation
scaffolding for the convention, not part of the `sqlite3-legacy-alternate`
build target.
