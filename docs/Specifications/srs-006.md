# SRS-006: Subsystem Namespace Prefix Convention

Where [srs-004](srs-004.md) gives every internal symbol under `src/sqlite/` a
flat `sqlite3_<snake_case>` shape, srs-006 inserts one more segment
identifying which subsystem the symbol belongs to:
`sqlite3_<namespace>_<name>`. C has no real namespaces, so this is a naming
convention, not a language feature — the same role a `namespace` block plays
in the eventual C++ conversion ([srs-002](../../../../srs/002-cpp-conversion.md)
in the parent workspace), expressed the only way available to a `snake_case`
C identifier today.

## Relationship to the workspace library split

The parent workspace already has a ten-library split
([`srs/001-legacy-restructure-and-dynamic-linking.md`](../../../../srs/001-legacy-restructure-and-dynamic-linking.md)
§1.3) and a categorization pass that populates those libraries from this
project's container decomposition
([`srs/005-subsystem-population-from-legacy-alternate.md`](../../../../srs/005-subsystem-population-from-legacy-alternate.md)).
The module list below is **not** identical to that library list, on
purpose — namespace naming inside a symbol and physical library boundaries
are two different concerns that don't have to be reconciled:

| Module below | Nearest workspace library | Difference |
|---|---|---|
| `sqlite3-backend-os` | `sqlite3-backend-os` | same |
| `sqlite3-backend-memory` | folded into `sqlite3-utils` | split out as its own namespace here |
| `sqlite3-backend-filesystem` | folded into `sqlite3-backend-os` | split out as its own namespace here |
| `sqlite3-backend-utils` | `sqlite3-utils` | renamed for symmetry with the other `backend-*` segments |
| `sqlite3-backend-pager` | `sqlite3-backend-pager` | same |
| `sqlite3-backend-btree` | `sqlite3-backend-tree` | `btree` instead of `tree` |
| `sqlite3-core-virtual-machine` | `sqlite3-core-virtual-machine` | same |
| `sqlite3-core-command-processor` (+3 children) | `sqlite3-core-command-processor` + 3 sibling `sqlite3-compiler-*` libraries | children nested under the parent segment here, not siblings |
| `sqlite3-interface` | `sqlite3-core-interface` | `core` dropped |

If the two are ever reconciled, rule 2 below makes that cheap: it reuses the
same usage-ranked-origin method srs-005 §3.1 already validated (`grep`-count
each symbol's whole-word occurrences across the pristine
`sqlite-src-3530400/src` tree, take the highest-count file as origin, map
that file to a module), so a future pass could recompute either taxonomy
from the same input. This document doesn't attempt that reconciliation —
it defines a symbol-naming convention, independent of where a `.c`/`.h` pair
physically lives.

## Rules

1. **The genuine public API is exempt**, the same carve-out srs-004 rule 4
   makes for `snake_case`. Symbols declared in the real upstream `sqlite3.h`
   and exercised externally — `sqlite3_open`, `sqlite3_prepare_v2`,
   `sqlite3_step`, `sqlite3_malloc`, `sqlite3_vfs`, `sqlite3_stmt`,
   `sqlite3_str`, `sqlite3_pcache_methods2`, ... — keep the plain
   `sqlite3_<name>` form. Inserting a namespace segment into a symbol
   external callers already link against by name would break the ABI
   compatibility that prefix exists for
   ([`verify/main.c`](../../verify/main.c) only ever calls this exempt
   surface — see srs-003/srs-004 for why that matters). Only internal-only
   symbols — the ones srs-004 already renamed to `sqlite3_btree_open`,
   `sqlite3_pager_get`, `wal_index_hash`, and the like precisely because
   they *aren't* part of that surface — get a namespace segment.

2. **A symbol's module is decided by ownership, not chosen independently.**
   For a type's methods, it's the module of the header that type lives in
   under [srs-003](srs-003.md) rule 2 (a `Btree.h` method is
   `backend-btree`, full stop). For a standalone multi-TU utility
   (srs-003 rule 3's second case) or a bare primitive typedef with no
   owning type, it's the module of whichever original SQLite source file
   the symbol's name occurs in most — the same usage-ranked-origin method
   referenced above.

3. **A segment is the module name with dashes replaced by underscores,
   inserted directly after `sqlite3_`**: `sqlite3_<segment>_<rest-of-name>`.
   A `Btree.h` function under `sqlite3-backend-btree` becomes
   `sqlite3_backend_btree_open`, not `sqlite3_btree_backend_open` — the
   segment always comes first so every symbol in one module sorts and
   greps together (`grep 'sqlite3_backend_btree_' src/sqlite/*.c` finds the
   whole module).

4. **`core-command-processor`'s three children nest under their parent's
   segment**: `sqlite3_core_command_processor_code_generator_<name>`, not
   `sqlite3_code_generator_<name>`. This is a deliberate difference from the
   workspace library layout (§ table above), where the three `compiler-*`
   libraries are independent siblings rather than children of
   `core-command-processor` — nesting here just reflects that all four
   segments are naming one family of concerns in the symbol itself, without
   implying anything about how they'd be split into build targets.

## Modules

| # | Module | Segment | Scope | Representative containers already in `src/sqlite/` |
|---|---|---|---|---|
| 1 | `sqlite3-backend-os` | `backend_os` | OS abstraction dispatch — the indirection through a VFS's function-pointer tables, not the concrete syscalls behind them (that's #3) | `sqlite3_vfs`, `sqlite3_io_methods`, `SQLiteThread` |
| 2 | `sqlite3-backend-memory` | `backend_memory` | Allocator, lookaside, and heap-hook internals | `Mem0Global`, `BenignMallocHooks`, `sqlite3_mem_methods` (exempt where public), `Lookaside`, `LookasideSlot` |
| 3 | `sqlite3-backend-filesystem` | `backend_filesystem` | Concrete VFS implementations that actually touch the kernel or emulate a filesystem in memory | `unixFile`, `unixFileId`, `unixInodeInfo`, `unixShm`, `unixShmNode`, `unix_syscall`, `UnixUnusedFd`, `MemFS`, `MemFile`, `MemJournal`, `FileChunk`, `FilePoint` |
| 4 | `sqlite3-backend-utils` | `backend_utils` | Generic, subsystem-agnostic helpers used tree-wide | `Hash`/`HashElem`, `StrAccum`, `PrintfArguments`, `RCStr`, `VList`, `sqlite3_str` (exempt where public), `DateTime`, `FpDecode`, `LogEst`, `BitMask`, `Bitvec`, the primitive typedefs (`u8`/`u16`/`u32`/`u64`/`i8`/`i16`/`i32`/`i64`/`Pgno`) |
| 5 | `sqlite3-backend-pager` | `backend_pager` | Page cache, WAL, rollback journal | `Pager`, `PagerSavepoint`, `Wal` + `Wal*` family, `DbPage`, `PgHdr`/`PgHdr1`/`PgFreeslot`, `PCache`/`PCache1`, `Savepoint` |
| 6 | `sqlite3-backend-btree` | `backend_btree` | B-tree, page-level cursors and payloads | `Btree`, `BtShared`, `BtCursor`, `BtreePayload`, `BtLock`, `CellInfo`, `CellArray`, `MemPage`, `KeyInfo`, `UnpackedRecord` |
| 7 | `sqlite3-core-virtual-machine` | `core_virtual_machine` | Bytecode interpreter, program construction, register (`Mem`) handling, external sorting | `Vdbe`, `VdbeCursor`, `VdbeFrame`, `VdbeOp`/`VdbeOpList`, `VdbeSorter` + sorter family (`SorterRecord`/`SorterFile`/`SorterList`, `PmaReader`/`PmaWriter`, `MergeEngine`, `IncrMerger`, `SortSubtask`, `SortCtx`), `VdbeTxtBlbCache`, `Mem`, `Op`, `SubProgram`, `SubrtnSig` |
| 8 | `sqlite3-core-command-processor` | `core_command_processor` | Statement orchestration state not specific to one child below | `Parse`, `ParseCleanup`, `Token`, `RenameToken`, `RenameCtx`, `NameContext` |
| 8.1 | `sqlite3-core-command-processor-code-generator` | `core_command_processor_code_generator` | AST → VDBE bytecode: query planning and expression/statement codegen | `Expr`/`ExprList`, `Select`/`SelectDest`, `Where*` family, `Window*` family, `AggInfo`(+`_col`/`_func`), `Upsert`, `Returning`, `TreeView`, `SrcList`/`SrcItem`, `IdList`, `Table`/`Column`/`Index`/`FKey`/`Trigger*` family, `With`/`Cte`/`CteUse` |
| 8.2 | `sqlite3-core-command-processor-parser` | `core_command_processor_parser` | Generated LALR grammar/parser tables | `yyParser`, `yyStackEntry`, `YYMINORTYPE`, `YyAction` |
| 8.3 | `sqlite3-core-command-processor-tokenizer` | `core_command_processor_tokenizer` | Token scanning | the `Token`-consuming scan functions (`sqlite3GetToken`-equivalent) |
| 9 | `sqlite3-interface` | `interface` | Public-API glue: connection/object lifecycle, extension loading, backup, auth callbacks — the internal helpers implementing the exempt public surface, not the exempt surface itself | `Sqlite3Config`, `InitData`, `AuthContext`, `BusyHandler`, `CollSeq`, `FuncDef`(+`Hash`/`Destructor`), `Module`, `VTable`, `Schema`, `Db` |

Row 9's scope note matters: rule 1 exempts individual public-API *symbols*
wherever they're declared; `sqlite3-interface` is the namespace for the
non-exempt internal machinery that *backs* those symbols (`Db.h`'s internal
helpers, not `sqlite3_open` itself).

## Tooling

Not yet built. The natural shape, following srs-004's precedent, is a
companion to `clang-refactor-enforce-naming.py` that consumes a
container→module mapping (produced by rule 2's usage-ranked-origin method,
the same one srs-005 §3.1 already implemented and validated against this
same source tree) and does the identifier rename plus reference update the
same libclang/clang-tidy way. It depends on srs-004 landing first, since it
renames the post-srs-004 `sqlite3_<snake>` form, not the current
`sqlite3<Camel>`/camelCase one.

## Status

Not yet applied — srs-004 (its prerequisite) is itself not yet applied. This
document defines the convention and the module table; no symbol under
`src/sqlite/` carries a namespace segment yet.
