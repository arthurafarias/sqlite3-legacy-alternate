# SRS-009: Amalgamation Macro-Literal Restoration

Every constant group SQLite originally spelled as a block of `#define`s
(`SQLITE_OPEN_*`, `SQLITE_LOCK_*`, extended result codes, ...) now exists in
this tree as a proper C `enum` under `src/sqlite/*.h`, carrying the exact
original macro name as its enumerator spelling — the "removing preprocessor
trash" pass already did that conversion. What it didn't touch is the
*call sites*: `src/sqlite/` was split out of a **preprocessed** dump of the
amalgamation (see [architecture.md](../architecture.md#starting-point)), so
by the time this tree existed, every `#define`-based constant referenced
inside a function body had already been expanded to its raw numeric value —
the symbolic name was gone from the token stream before the split ever
happened. The enum conversion re-created the *declarations*; it never went
back and restored the *uses*. srs-009 is that second half: wherever a
function body still holds a bare number that used to be a named constant,
and an enum constant with that exact name and value already exists
somewhere in the tree, replace the number with the name.

## Relationship to prior SRS

- This reuses the tree-wide enum work already done rather than duplicating
  it — no new enum is created by this pass. If a numeric literal doesn't
  match any enum constant already declared under `src/sqlite/*.h`, it's out
  of scope here, not a gap this SRS tries to close (rule 2).
- Independent of the container-migration concerns in
  [srs-003](srs-003.md)/[srs-004](srs-004.md)/[srs-005](srs-005.md)/
  [srs-006](srs-006.md) — this pass never moves or renames a symbol, it only
  rewrites an expression *inside* a function body that's already sitting in
  its correct file. It also doesn't care whether that file is a proper
  one-symbol container or (for the ~478 functions the old scope of this
  document covered) still sitting inline in `sqlite3.c` — both are function
  bodies under `src/sqlite/`, and both are in scope. Restoring a literal to
  `SQLITE_OPEN_READONLY` doesn't depend on `sqlite3.c` having been split
  apart first, so this SRS number was reassigned to this pass rather than
  waiting on that migration; the function-body migration that previously
  occupied srs-009 has no requirements document yet.
- Order relative to [srs-008](srs-008.md) (warning-clean compilation)
  doesn't matter: srs-008's parenthesization and char-subscript fixes are
  formatting-only and don't touch integer literal values, so this pass can
  land before or after it without conflict.

## Source of truth

The "original" side of every comparison this SRS makes is a real,
never-preprocessed build of the SQLite 3.53.4 amalgamation — the same
`sqlite3.c` any application embeds and compiles directly, not
`sqlite3.E.c`/`sqlite3.p.c` (the macro-expanded dump the seed pass actually
split, which no longer exists in the tree — see the historical
`c7dd230` commit in the parent workspace if it's ever needed again). Using
the real amalgamation instead of regenerating that preprocessed dump is
deliberate: a lexer sees a macro *invocation* exactly the way the amalgamation's
authors wrote it (`SQLITE_OPEN_READONLY`, still an identifier token) whether
or not the file has been run through cpp — libclang's tokenizer reports the
token spelling as written in the source, not the macro's expansion, so
tokenizing the real amalgamation directly gets the original symbolic name
without needing to reconstruct the exact preprocessing flags the seed pass
used.

## Method

For every function name that exists both in the real amalgamation and
somewhere under `src/sqlite/` today:

1. Tokenize both bodies (libclang, not a hand-rolled lexer — comments and
   whitespace are already excluded, and every token carries its precise
   source extent).
2. Align the two token-spelling sequences with a sequence diff
   (`difflib.SequenceMatcher`). Everything outside a `replace` block is
   either identical between the two trees or a mechanical difference some
   other pass already introduced (a removed `((void)(0));` from
   [srs-008](srs-008.md)'s dead-noop cleanup, a parenthesization fix, ...) —
   ignored either way, since this SRS only ever touches single-token
   replacements.
3. A `replace` block is a candidate **only** when it substitutes exactly one
   token for exactly one token, the original token is an `IDENTIFIER`, and
   the current token is an integer `LITERAL`.
4. The identifier must name an enum constant that already exists somewhere
   under `src/sqlite/*.h`, and that constant's value must equal the current
   literal's value. Both checks are load-bearing: the first keeps this pass
   from inventing a new constant (rule below), the second catches a
   coincidental token-alignment that isn't actually the same constant (a
   diff artifact, not a real correspondence).

Anything that doesn't clear all four steps — a function that doesn't exist
by the same name in both trees, a multi-token replacement, an identifier
that isn't a known constant, a value mismatch — is left untouched and
counted, not guessed at. This is the same "highest-confidence bucket only"
posture [the old scope of this document](#relationship-to-prior-srs) and
[srs-005](srs-005.md) both take: a pass that silently drops ambiguous sites
into a report is more useful than one that guesses and gets some of them
wrong.

## Rules

1. **Scope is function bodies only, tree-wide.** Every `.c` file under
   `src/sqlite/` is in scope, including `sqlite3.c` itself — this pass does
   not wait on that file being split apart first (see Relationship to prior
   SRS). Declarations, struct field initializers outside a function body,
   and macro definitions themselves are out of scope; the method above only
   ever walks tokens inside a `FUNCTION_DECL`'s extent.

2. **Only enum constants that already exist are used — never create a new
   one.** If a literal in the current tree matches a `#define` in the real
   amalgamation but no enum constant of that name exists anywhere under
   `src/sqlite/*.h` (the constant group was never converted, or was
   converted under a different spelling), the site is left alone and
   counted separately from the applied candidates. Adding the missing enum
   is a different, larger decision than this SRS makes.

3. **A restored site keeps working with whatever header already declares
   the constant — no data ownership decision is made here.** If the
   constant's home header (`sqlite/SqliteOpenFlags.h`, ...) isn't already
   `#include`d by the file receiving the substitution, the include is added
   directly (there is no repeatable tool for this the way
   `clang-refactor-remove-all-h.py` handles system/container includes for
   *type* references — see [architecture.md](../architecture.md#the-refactor-toolchain) —
   since that script only resolves includes for files still on the retired
   `_All.h` convention). The apply phase (below) does this per file as part
   of the same edit, not as a follow-up pass.

4. **Ambiguous value collisions are never guessed at.** Two enum constants
   can share a value on purpose (`SQLITE_OPEN_SUPER_JOURNAL` and
   `SQLITE_OPEN_MASTER_JOURNAL` both `0x00004000` — see
   [`SqliteOpenFlags.h`](../../src/sqlite/SqliteOpenFlags.h)). This never
   becomes a real ambiguity for this pass, because the substitution is
   driven by the *name* the original amalgamation actually used at that
   call site (step 3-4 of Method), not by searching for any constant whose
   value happens to match — the value check is a correctness gate on an
   already-chosen name, not a search key.

5. **Classification and application are two separate, re-runnable
   passes**, matching every prior mechanical SRS in this directory. Classify
   never writes to `src/sqlite/`; apply only ever consumes a classify
   report, never re-derives candidates itself. Re-running classify after a
   partial apply should report a shrinking, disjoint remainder.

## Tooling

Extends `tools/clang-refactor/` with a new pair, following the existing
report/apply shape (see
[architecture.md](../architecture.md#the-refactor-toolchain)):

- [`clang-refactor-classify-macro-literals.py`](../../tools/clang-refactor/clang-refactor-classify-macro-literals.py) —
  read-only. Builds the known-constant table by parsing every
  `src/sqlite/*.h` and reading each `ENUM_CONSTANT_DECL`'s libclang-evaluated
  `enum_value` (so constant expressions like
  `SQLITE_ERROR_MISSING_COLLSEQ = (SQLITE_ERROR | (1 << 8))` in
  [`SqliteExtendedResultCode.h`](../../src/sqlite/SqliteExtendedResultCode.h)
  resolve correctly without this script needing its own C constant-expression
  evaluator); parses the real amalgamation
  (`--original-src`, default `/home/arthur/Downloads/sqlite-src-3530400/sqlite3.c` —
  an external, unmodified SQLite 3.53.4 source tree, not part of this
  repository) and every file in `compile_commands.json` under
  `src/sqlite/`; runs the Method above; writes
  `tools/clang-refactor/macro-literals-report.json`, plus a stats block
  (functions matched in both trees, multi-token blocks skipped, identifiers
  that resolved to no known constant, value mismatches) so a re-run can be
  compared against the last one.
- `clang-refactor-apply-macro-literals.py` — consumes that report. Per file,
  sorts candidates by descending source offset and splices in the constant
  name in place of the literal text (offset-descending, no dependency on
  `clang-apply-replacements`, matching
  [srs-005](srs-005.md#tooling)'s apply step); before writing, checks
  whether the candidate's `header` is already `#include`d and inserts it
  next to the file's other `sqlite/*.h` includes if not (rule 3). Runs
  `clang-format` over every touched file afterward, matching every other
  apply script in the directory.

No new AST-matching logic beyond what a token-sequence diff plus libclang's
own enum-constant evaluation already provide — this is a smaller problem
than any of the struct/function relocation passes in this directory, not a
new category of tool.

## Baseline

Produced by `clang-refactor-classify-macro-literals.py`'s report phase
against the tree as it stood before this pass was applied:

```sh
python3 tools/clang-refactor/clang-refactor-classify-macro-literals.py
```

| | Count |
|---|---:|
| Enum constants known to the tree (`src/sqlite/*.h`) | 514 |
| Function definitions in the real amalgamation | 2,604 |
| Function definitions in the current tree (`compile_commands.json`) | 2,624 |
| Functions present, by name, in both trees | 2,604 |
| — of those, with at least one candidate site | 758 |
| Candidate substitution sites | 2,535 |
| Multi-token `replace` blocks skipped (not 1:1 alignable) | 3,588 |
| Identifier not a known constant (macro never enum-ified, or renamed) | 6,904 |
| Value mismatch (name matched, value didn't — diff-alignment noise) | 7 |

One tokenizer quirk surfaced and was worked around while building the
classify phase: `clang_tokenize` ignored its own extent for a small number
of cursors in the real amalgamation (`sqlite3PagerCommitPhaseOne`'s
219-line/~9KB extent came back with 228,659 tokens — effectively the rest
of the 9.5MB file). `tokenize_function()` now drops any token whose own
extent falls outside the cursor's extent rather than trusting the raw
result; see the comment at its definition for the observed case.

## Status

Applied. All 2,535 candidate sites from the Baseline table were substituted
across 59 files (`clang-refactor-apply-macro-literals.py --apply`), 171
`#include`s were added for headers not already pulled in at the receiving
file, `clang-format` ran over every touched file, and the tree rebuilds
clean (`-Wall -pedantic -Werror`, zero warnings) with
`sqlite3-legacy-alternate-verify` passing under `ctest`. See
[Applying](#applying) for the exact commands run.

## Applying

1. Run the classify phase and inspect the report:

   ```sh
   python3 tools/clang-refactor/clang-refactor-classify-macro-literals.py
   ```

2. Apply the surviving candidates:

   ```sh
   python3 tools/clang-refactor/clang-refactor-apply-macro-literals.py
   ```

3. Rebuild and verify, the same check every prior SRS in this directory
   ends on:

   ```sh
   cmake -S . -B build
   cmake --build build
   ctest --test-dir build --output-on-failure
   ```

   A passing `sqlite3-legacy-alternate-verify` run confirms the substitution
   didn't change observable behavior — restoring a constant's name is not
   supposed to change what a function does, only how it reads.
4. Re-run the classify phase; confirm the report's candidate count is zero
   and that the remaining `identifier_not_a_known_constant`/`value_mismatch`
   counts are stable across runs (not evidence of a bug — see rule 2).
